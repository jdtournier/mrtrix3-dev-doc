1 Command-line parsing {#command_line_parsing}
2 ====================
3 
4 Overview {#command_line_overview}
5 ========
6 
7 Command-line parsing in MRtrix is based on a set of fairly generic conventions
8 to maximise consistency for end-users, and convenience for developers. A
9 command is expected to accept a certain number of arguments, and a certain
10 number of options. These are specified in the code using the MR::App::ARGUMENTS and
11 MR::App::OPTIONS vectors. They are also used to generate the help page for the
12 application, and it is therefore sensible to provide as much information in the
13 description fields as neccessary for end-users to understand how to use the
14 command.
15 
16 Arguments and options are specified within the usage() function of each command
17 (see @ref command_howto for details). Arguments are supplied as a vector of
18 MR::App::Argument objects, and by default each MR::App::Argument is expected to
19 have its value supplied on the command-line (although one argument can be
20 made optional, or allowed to be supplied multiple times).
21 
22 Options are supplied as a vector of MR::App::Option objects, and by default are
23 optional (although they can be specified as 'required'). By default, only one
24 instance of each option is allowed, but this can also be changed. Options may
25 also accept additional arguments, which should be supplied immediately after
26 the option itself.
27 
28 Parsing of the command-line is done by first identifying any options supplied
29 and inserting them into the option list, along with their corresponding
30 arguments (if any). All remaining tokens are taken to be arguments, and
31 inserted into the MR::App::argument list. Checks are performed at this stage
32 to ensure the number of arguments and options supplied is consistent with that
33 specified in the usage() function.
34 
35 The values of these arguments and options can be retrieved within the
36 application using the MR::App::argument list and the MR::App::option list.
37 Note that in practice, the MR::App::get_options() method is a much more
38 convenient way of querying the command-line options.
39 
40 
41 An overview of the basic contents of an application is given in @ref
42 command_howto. The description and syntax of the command should be fully
43 specified in the usage() function, and the various arguments and options can
44 then be retrieved and used in the application. Each of these aspects is
45 described below.

50 Specifying the description and syntax {#command_line_usage}
51 =====================================
52 
53 The role of the usage() function is to populate the MR::App::DESCRIPTION,
54 MR::App::ARGUMENTS, and MR::App::OPTIONS vectors, and optionally the
55 MR::App::VERSION, MR::App::AUTHOR, and MR::App::COPYRIGHT entries if default
56 values are not suitable. The example below illustrates a basic usage()
57 function:
58 
59 ~~~{.cpp}
60 #include "app.h"
61 
62 using namespace MR;
63 using namespace App;
64 
65 void usage ()
66 {
67  VERSION[0] = 1; // these are optional,
68  VERSION[1] = 2; // and will default to the
69  VERSION[2] = 3; // MRtrix core version if ommitted
70 
71  // optional, defaults to J-Donald Tournier
72  AUTHOR = "Joe Bloggs (j.bloggs@bogus.org)";
73 
74  // optional, defaults to the MRtrix GPL disclaimer
75  COPYRIGHT = "Copyright 1967 The Institute of Bogus Science";
76 
77  DESCRIPTION
78  + "A brief description of the command";
79 
80  ARGUMENTS
81  + Argument ("input", "the input image").type_image_in();
82 
83  OPTIONS
84  + Option ("myopt",
85  "my option to this command. Takes one additional float argument.")
86  + Argument ("value");
87 }
88 ~~~

91 The DESCRIPTION {#command_line_description}
92 ===============
93 
94 As shown in the example, description entries are added to the
95 MR::App::DESCRIPTION vector using the `+` operator, and consist of `const
96 char*` strings. Each separate string will be formatted into a distinct
97 paragraph on the help page.
98 
99 
100 The ARGUMENTS {#command_line_arguments}
101 =============
102 
103 As shown in the example, individual command-line arguments are added to the
104 MR::App::ARGUMENTS vector as MR::App::Argument objects using the `+` operator.
105 As a minimum, each Argument is constructed with its short-hand name (used in
106 the syntax line), and its description, which will appear in a separate listing
107 after the syntax line.
108 
109 By default, an Argument is typed as a string. There are a number of other types
110 that can be used, and each type will perform its own checks on the values
111 provided by the user. For example:
112 
113 ~~~{.cpp}
114 ARGUMENTS
115 + Argument ("input",
116  "a description of the input argument")
117  .type_integer (0, 8, 16);
118 ~~~
119 
120 The type specifiers that can be used are:
121 
122 - [type_text()](@ref MR::App::Argument::type_text()):
123  the default.
124 
125 
126 - [type_image_in()](@ref MR::App::Argument::type_image_in()):
127  the argument corresponds to an already-existing image that
128  will be used as an input. The argument value will be retrieved as a string
129  corresponding to the image specifier.
130 
131 - [type_image_out()](@ref MR::App::Argument::type_image_out()):
132  argument corresponds to a non-existing image that will be produced by the
133  program. The argument value will be retrieved as a string corresponding to
134  the image specifier.
135 
136 - [type_integer()](@ref MR::App::Argument::type_integer()):
137  the argument corresponds to an integer value in the range [minimum, maximum],
138  with default value as specified. The argument value will be retrieved as an
139  int. If (minimum, default, maximum) are ommitted, default values will be
140  used.
141 
142 - [type_float(minimum, default, maximum)](@ref MR::App::Argument::type_float()):
143  the argument corresponds to a floating-point value in the range [minimum,
144  maximum], with default value as specified. The argument value will be retrieved
145  as a float or double. If (minimum, default, maximum) are ommitted, default
146  values will be used.
147 
148 - [type_choice()](@ref MR::App::Argument::type_choice()) (list):
149  the argument corresponds to one of a set number of available choices,
150  supplied as a NULL-terminated array of strings. The argument value can be
151  retrieved as a string or as an int, corresponding to the appropriate index into
152  the list of choices.
153 
154 - [type_sequence_int()](@ref MR::App::Argument::type_sequence_int()):
155  the argument corresponds to a sequence of integers. The argument value will
156  be retrieved as a `std::vector<int>`.
157 
158 - [type_sequence_float()](@ref MR::App::Argument::type_sequence_float()):
159  the argument corresponds to a sequence of floating-point values. The argument
160  value will be retrieved as a `std::vector<float>`.
161 
162 In certain cases, it is possible that none of these types are suitable. In
163 these cases, the default type ([type_text()](@ref
164 MR::App::Argument::type_text())) should be used, and any custom casting and
165 checking will need to be performed explicitly by the programmer.
166 
167 It is possible to specify at most one argument as being optional, by adding
168 the [optional()](@ref MR::App::Argument::optional()) flag:
169 
170 ~~~{.cpp}
171 ARGUMENTS
172 + Argument ("input",
173  "a description of the input argument")
174  .optional();
175 ~~~
176 
177 Finally, at most one argument can be specified as repeatable (in other words, a
178 number of these arguments can be supplied one after the other). This is useful
179 for example if the command can operate on multiple data sets sequentially:
180 
181 ~~~{.cpp}
182 ARGUMENTS
183 + Argument ("input",
184  "a description of the input argument")
185  .allow_multiple();
186 ~~~

189 The OPTIONS {#command_line_options}
190 ===========
191 
192 Individual command-line options are added to the OPTIONS vector as MR::App::Option
193 objects using the `+` operator. As a minimum, each Option is constructed with
194 its short-hand name (used on the command-line), and its description:
195 
196 ~~~{.cpp}
197 OPTIONS
198 + Option ("option", "a description of the option");
199 ~~~
200 
201 Similarly to arguments, options can be specified as [repeatable](@ref MR::App::Option::allow_multiple()):
202 
203 ~~~{.cpp}
204 OPTIONS
205 + Option ("option", "a description of the option").allow_multiple();
206 ~~~
207 
208 Options can also be specified as [required](@ref MR::App::Option::required()) (by default, options are optional):
209 
210 ~~~{.cpp}
211 OPTIONS
212 + Option ("option", "a description of the option").required();
213 ~~~
214 
215 To handle additional arguments to an MR::App::Option, arguments can be added to the
216 option as MR::App::Argument objects, again using the `+` operator. Note that in
217 this case the description field of the argument is ignored, and so does not
218 need to be specified: These Arguments can be typed in the same way as regular
219 MR::App::Arguments. For example:
220 
221 ~~~{.cpp}
222 OPTIONS
223 + Option ("option", "a description of the option")
224  + Argument ("value").type_integer ()
225  + Argument ("list").type_sequence_int ();
226 ~~~

229 Defining option groups {#command_line_option_group}
230 ----------------------
231 
232 Option objects are actually inserted into MR::App::OptionGroup objects; in the
233 example above, new Options were added to the default MR::App::OptionGroup. It
234 is possible to create new option groups that will appear under their own
235 heading in the help page.
236 
237 ~~~{.cpp}
238 OPTIONS
239 + Option ("normal", "a 'standard' option")
240 
241 + OptionGroup ("My options")
242 
243 + Option ("check",
244  "this option will now appear in the 'My options' section);
245 ~~~
246 
247 This makes it possible to define OptionGroup objects for commonly-used
248 functions elsewhere in the code, and simply add them into the application when
249 required. For example:
250 
251 ~~~{.cpp}
252 // funny_processing.h:
253 
254 extern const OptionGroup funny_options;
255 ~~~
256 
257 ~~~{.cpp}
258 // funny_processing.cpp:
259 
260 const OptionGroup funny_options ("Funny options")
261 + Option ("joke", "a option that is now part of the funny options)
262 + Argument ("name")
263 
264 + Option ("prank", "another option");
265 ~~~
266 
267 
268 ~~~{.cpp}
269 // my_application.cpp:
270 
271 void usage ()
272 {
273  ...
274 
275  OPTIONS
276  + Option ("normal", "a 'standard' option")
277 
278  + funny_options;
279 }
280 ~~~
281 
282 This is particularly useful since these options can then be handled by the
283 relevant functions or classes, without the developer of the application
284 needing to worry about them in any way. Following on from the example above,
285 the 'funny_processing' code might declare a function 'do_funny_processing()',
286 which could then retrieve any relevant parameters supplied by the user on the
287 command-line, with no interaction with the body of the application using that
288 function (other than adding the relevant OptionGroup to the OPTIONS list):
289 
290 ~~~{.cpp}
291 // funny_processing.cpp:
292 
293 void do_funny_processing ()
294 {
295  App::Options opt = App::get_options ("joke");
296  if (opt.size()) {
297  // do something else...
298  }
299 
300  ...
301 }
302 ~~~

304 Breaking up an option group into multiple lists {#command_line_option_group_broken_up}
305 ===============================================
306 
307 In some cases, it might be useful to break up an MR::App::OptionGroup into
308 several distinct sub-groups, even though they would all conceptually belong to
309 the same section. For instance, some options might only be required when
310 processing input data, others when producing output data. Some applications
311 might only need to process data without producing any, others might only
312 produce data, and others might need to do both. To support this, developers can
313 provide several OptionGroups with identical sections names; these will then be
314 displayed together in the help page if used together in the corresponding
315 application.
316 
317 For example:
318 
319 ~~~{.cpp}
320 // funny_processing.h:
321 
322 extern const OptionGroup funny_options_in;
323 extern const OptionGroup funny_options_out;
324 ~~~
325 
326 ~~~{.cpp}
327 // funny_processing.cpp:
328 
329 const OptionGroup funny_options_in ("Funny options")
330 + Option ("funny_in", "specify funny input data")
331 + Argument ("name");
332 
333 // Note that the group heading is the same in both cases:
334 const OptionGroup funny_options_out ("Funny options")
335 + Option ("funny_out", "specify funny output data")
336 + Argument ("name");
337 ~~~
338 
339 ~~~{.cpp}
340 // my_application.cpp:
341 
342 void usage ()
343 {
344  ...
345 
346  OPTIONS
347  + Option ("normal", "a 'standard' option")
348 
349  // these will both now appear under the same heading "Funny options" on the
350  // help page, with the options themselves appearing in the order listed here:
351  + funny_options_in
352  + funny_options_out;
353 }
354 ~~~

358 Retrieving command-line argument and option values {#command_line_retrieve}
359 ==================================================
360 
361 Argument and option values can be retrieved at any point within the
362 application. Arguments are provided via the MR::App::argument vector, which is
363 a `std::vector<App::ParsedArgument>`. Their values can be retrieved using the
364 subscript operator, indexed by their position on the command-line. For
365 convenience, values can be obtained directly by implicit type-casting (i.e.
366 simply by using the argument in a context that requires the relevant type -
367 e.g. assignment). The following examples should clarify how this is done:
368 
369 ~~~{.cpp}
370 void run () {
371  size_t numarg = argument.size(); // the number of arguments
372 
373  // retrieving values as a string:
374  auto header = Header::open (argument[0]);
375 
376  // retrieving value by implicit type-casting:
377  // Note that this argument is expected to have been specified using type_integer().
378  // Bound checks are performed at this stage.
379  int value = argument[1];
380 
381  // Another example of retrieval via implicit type-casting:
382  // Note that in this case, the argument is expected to have been specified using type_sequence_int()
383  std::vector<int> list = argument[2];
384 
385  ...
386 }
387 ~~~
388 
389 Option values are most easily retrieved using the MR::App::get_options()
390 convenience function. This returns a MR::App::Options object that is to all
391 intents and purposes identical in use to a `std::vector<std::vector<App::ParsedArgument>>`:
392 one vector of values for each matching option specified on the command-line (an
393 option may be specified multiple times if it has been specified using
394 allow_multiple()). The values are stored in the same way as the parsed
395 arguments, and their values can therefore also be retrieved using implicit
396 type-casting (see above). The example below should clarify this:
397 
398 ~~~{.cpp}
399 void run () {
400  Options opt = get_options ("option");
401 
402  if (opt.size()) { // check whether any such options have been supplied
403  // retrieve first argument of first option as an int:
404  int value = opt[0][0];
405 
406  // retrieve second argument of first option as a sequence of ints:
407  std::vector<int> list = opt[0][1];
408  }
409 
410  // in cases where the option has been specified using allow_multiple(),
411  // opt.size() will return the number of such options.
412  // In this example, the first argument of each additional option is added
413  // to the list of values by implicit type-casting to a float:
414  opt = get_options ("multiple_option");
415  std::vector<float> values;
416  for (size_t n = 0; n < opt.size(); ++n)
417  values.push_back (opt[n][0]);
418 
419  ...
420 }
421 ~~~
422 
423 A common use-case is to set a variable from the command-line, defaulting
424 to a set value otherwise. This can be done using the
425 MR::App::get_option_value() convenience call. For example:
426 
427 ~~~{.cpp}
428 void run() {
429  // param will be set to 0.0 unless the otherwise stated via the 'parameter' option:
430  const float param = get_option_value ("parameter", 0.0);
431 
432  ...
433 }
434 ~~~
435 
436 If for any reason the get_options() convenience function is not suitable,
437 options can be accessed directly using the MR::App::option variable, which is
438 a `std::vector` of MR::App::ParsedOption objects, one per option in the same
439 order as on the command-line. Note that in this case, option values will only
440 be available as `const char*` string arrays, and no bounds checking will be
441 performed. For further details, refer to the MR::App::ParsedOption description
442 page.
