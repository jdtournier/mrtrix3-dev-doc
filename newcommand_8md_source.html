1 Creating a new MRtrix command {#command_howto}
2 =============================
3 
4 The anatomy of a command {#command_layout}
5 ========================
6 
7 In MRtrix, each command corresponds to a source file (`*.cpp`), placed in the
8 `cmd/` folder, named identically to the desired application name (with the
9 `.cpp` suffix). The file should contain the following sections:
10 
11 First, the relevant headers should be included. This will include at least
12 `lib/command.h` file, which includes the relevant code for executables.
13 ~~~{.cpp}
14 #include "command.h"
15 ~~~
16 
17 Note that the `lib/` folder is in the default search path. See
18 @ref include_path for details.
19 
20 At this point, it is helpful to bring the `MR` & `MR::App` namespaces within
21 the current scope:
22 ~~~{.cpp}
23 using namespace MR;
24 using namespace App;
25 ~~~
26 
27 Information about the application and its syntax is provided in the usage()
28 function (described in more detail [in this section](@ref command_line_usage)):
29 ~~~{.cpp}
30 void usage () {
31 ~~~
32 
33 In this function, you can optionally set the author and copyright fields, which
34 will be displayed when the command is invoked with the `-version` option. If
35 ommitted, the author field will default to "J-Donald Tournier", and the
36 copyright notice will default to that of the MRtrix core.
37 ~~~{.cpp}
38  AUTHOR = "Joe Bloggs";
39 
40  COPYRIGHT = "whatever you want";
41 ~~~
42 
43 The version information is obtained from the files `lib/version.h` (for the
44 MRtrix core) and `src/project_version.h` (for external modules). Both of
45 these are automatically updated to use the [git](http://git-scm.com/)
46 version information if [git](http://git-scm.com/) installed - otherwise the
47 information already contained in these files will be used as-is. If you want
48 to set the version information for your module and can't use
49 [git](http://git-scm.com/), you can simply add the relevant information
50 in the file `src/project_version.h` within your project, e.g.:
51 
52 ~~~{.cpp}
53 #define MRTRIX_PROJECT_VERSION "my-version-1.0"
54 ~~~
55 
56 You should then set a brief description of the command. Each entry
57 corresponds to a new paragraph:
58 ~~~{.cpp}
59  DESCRIPTION
60 
61  + "This is used to illustrate how to write a command in MRtrix"
62 
63  + "This section is where you explain a bit more about your command, "
64  "its intended purpose, and any important pieces of information that "
65  " might not easily fit in the following sections";
66 ~~~
67 
68 Next, you should specify the arguments required by the command (see [this
69 section](@ref command_line_arguments) for more details). The first
70 entry for each argument is a brief name to appear on the syntax line. The
71 second entry is longer description that will appear immediately after to
72 explain what is expected in that argument.
73 ~~~{.cpp}
74  ARGUMENTS
75 
76  + Argument ("input",
77  "the input image."
78  ).type_image_in()
79 
80  + Argument ("param",
81  "the parameter controlling my algorithm."
82  ).type_float(0.0, 1.0, 10.0)
83 
84  + Argument ("output",
85  "the output image."
86  ).type_image_out();
87 ~~~
88 
89 Note that the expected type (and potentially allowed range) of each argument
90 can also be specified using the `type_*()` member functions. By default, each
91 argument is a string. Also, an option can be specified to be optional, or
92 that multiple such arguments are allowed. For more information, see the
93 [command-line parsing documentation](@ref command_line_arguments).
94 
95 Next, you can optionally specify any command-line options your command may
96 accept. As for the MR::App::Argument class, the first entry for each option is a
97 brief name, which in this case will be the name that the user will need to
98 use on the command-line to invoke the option. The second entry is the
99 description of the option. Optionally, each MR::App::Option can also have Arguments
100 added to it. In this case, the description field of the Argument is
101 ignored and should simply be ommitted.
102 ~~~{.cpp}
103  OPTIONS
104  + Option ("option1", "on option requiring two arguments")
105  + Argument ("arg1").type_integer (0,1,10)
106  + Argument ("arg2")
107 
108  + Option ("option2", "an option that does not take arguments");
109 }
110 ~~~
111 This marks the end of the usage() function.
112 
113 Actual processing will take place in the run() function. This function is
114 declared `void`, and should not return any value. Any errors should be handled
115 using C++ exceptions as described below. Note that any unhandled exception will
116 cause the program to terminate with a non-zero return value. Arguments and
117 options can be retrieved using the [argument](@ref MR::App::argument) vector
118 and [get_options()](@ref MR::App::get_options()) function:
119 ~~~{.cpp}
120 void run ()
121 {
122  auto in = Image<float> (argument[0]);
123 
124  auto opt = get_options ("option1");
125  int arg1;
126  std::string arg2;
127  if (opt.size()) {
128  arg1 = opt[0][0];
129  arg2 = opt[0][1];
130  }
131 
132  bool option2 = get_options ("option2").size();
133 
134 
135  // perform processing...
136 }
137 ~~~
138 Note that the retrieved arguments are implicitly type-cast to the requested
139 type, without any need for explicit conversion.
140 
141 It is also worth explaining that [get_options()](@ref MR::App::get_options())
142 returns a vector of vectors of arguments. The first index returns the instance
143 of the option (for cases where the same option can be specified multiple
144 times), and the second index returns the argument supplied at that position for
145 that instance of the option. For more information, see the
146 [command-line parsing documentation](@ref command_line_options).

150 Error handling {#error_handling}
151 ==============
152 
153 All error handling in MRtrix is done using C++ exceptions. MRtrix provides its
154 own MR::Exception class, which additionally allows an error message to be
155 displayed to the user. Developers are strongly encouraged to provide helpful
156 error messages, so that users can work out what has gone wrong more easily.
157 
158 The following is an example of an exception in use:
159 ~~~{.cpp}
160 void myfunc (float param)
161 {
162  if (isnan (param))
163  throw Exception ("NaN is not a valid parameter");
164  ...
165  // do something useful
166  ...
167 }
168 ~~~
169 
170 The strings helper functions can be used to provide more useful information:
171 
172 ~~~{.cpp}
173 void read_file (const std::string& filename, int64_t offset)
174 {
175  std::ifstream in (filename.c_str());
176  if (!in)
177  throw Exception ("error opening file \"" + filename + "\": " + strerror (errno));
178 
179  in.seekg (offset);
180  if (!in.good())
181  throw Exception ("error seeking to offset " + str(offset)
182  + " in file \"" + filename + "\": " + strerror (errno));
183  ...
184  // do something useful
185  ...
186 }
187 ~~~
188 
189 It is obviously possible to catch and handle these exceptions, as with
190 any C++ exception:
191 
192 ~~~{.cpp}
193 try {
194  read_file ("some_file.txt", 128);
195  // no errors, return OK:
196  return 0;
197 }
198 catch (Exception& E) {
199  FAIL ("error in processing - message was:");
200  E.display();
201  return 1;
202 }
203 ~~~
204 
205 @note the error message of an Exception will only be shown if it left uncaught,
206 or if it is explicitly displayed using its [display()](@ref MR::Exception::display())
207 member function.

210 Header search path {#include_path}
211 ==================
212 
213 By default, the search path provided to the compiler to look for headers
214 consists of the compiler's default path for system headers, any additional
215 paths identified by the `configure` script as necessary to meet dependencies
216 (e.g. Zlib or Eigen), and the `lib/` and `src/` folders. Headers should
217 therefore be included by their path relative to one of these folders. For
218 example, to include the file `lib/math/SH.h`, use the following:
219 ~~~{.cpp}
220 #include "math/SH.h"
221 ~~~
222 
223 Note that any MRtrix header must be supplied within quotes, as this signals to
224 the `build` script that this header should be taken into account when
225 generating the list of dependencies (see @ref build_section for details).
226 Conversely, any system headers must be supplied within angled brackets,
227 otherwise the `build` script will attempt (and fail) to locate it within the
228 MRtrix include folders (usually `lib/` and `src/`) to work out its
229 dependencies, etc. For example:
230 ~~~{.cpp}
231 // These are system headers, and will not be taken
232 // into account when working out dependencies:
233 #include <iostream>
234 #include <zlib.h>
235 
236 // These headers will be taken into account:
237 // any changes to these headers (or any header they themselves
238 // include) will cause the enclosing file to be recompiled
239 // the next time the build script encounters them.
240 #include "mrtrix.h"
241 #include "math/SH.h"
242 ~~~
243 
244 Note that this is also good practice, since it is the convention for
245 compilers to look within the system search path for headers included within
246 angled brackets first, whereas headers included within quotes will be searched
247 within the user search path first.
