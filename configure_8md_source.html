1 The configure script {#configure_page}
2 ====================
3 
4 The first step in compiling MRtrix is to invoke the configure script. This
5 will run a series of tests to ensure the required dependencies are installed,
6 and figure out the appropriate compilation settings. By default, this
7 information is stored in the \c release/config file, ready for use with the
8 [build script](@ref build_page).
9 
10 The configure script accepts a number of options, and is influenced by a
11 number of environment variables. These are all described in detail in
12 configure script's online help, produced by invoking it with the \c -help
13 ption:
14 
15  $ ./configure -help
16 
17 These options should be self-explanatory, and will not be described any
18 further here. This section instead focuses on describing the multi-build
19 feature of MRtrix.
20 
21 Using multiple co-existing configurations {#multiconfig}
22 =========================================
23 
24 By default, the configure script will generate a file called `release/config`,
25 with the relevant settings requested by the options supplied to the configure
26 script. This is a text file consisting of Python commands, which you're
27 encouraged to look through. It is possible to request that the information be
28 stored in a different folder, so that non-standard settings can be used to
29 build a different set of binaries, without affecting the existing set. This is
30 best illustrated with an example:
31 
32 If we want to generate a configuration for a debug build, the `-debug` option
33 can be passed to the configure script to generate a suitable configuration for
34 it. If we also supply a suitable name as an argument, the settings will be stored
35 in a file called `<name>/config` instead of the default `release/config`. In
36 our case, we chose the name `dbg`:
37 
38  $ ./configure -debug dbg
39 
40 This generates a folder called `dbg`, wihtin which the new `config` file resides.
41 This allows the new `dbg` config to co-exists with the default `release` build.
42 We can then ask the build script to compile the debug version of the binaries
43 by passing the name `dbg` as the target:
44 
45  $ ./build dbg
46 
47 To avoid naming conflicts with the existing binaries, all intermediate files
48 generated with this command will be placed in the `dbg` folder instead of the
49 default `release` folder. The debug version of the command can then be invoked
50 as, for example:
51 
52  $ dbg/bin/mrconvert in.mif out.nii
53 
54 
55 This allows any number of configurations to co-exist without interferring with
56 each other. Other potentially interesting configurations include:
57 
58 - one that is statically linked, configured with the `-static` option. This makes
59  it easy to install on target systems where the required dependencies cannot
60  be installed.
61 
62 - one that does not include the GUI components, configured with the `-nogui`
63  option.
64 
65 - one that does not include the MRtrix shared library, configured with the
66  `-noshared` option.
67 
68 - one that is built for a generic CPU, configured by setting the `ARCH`
69  environment variable. This makes it easy to deploy on other systems whose
70  exact CPU type might not match the system on which the executable are being
71  compiled. Note that by default, `./configure` will create a configuration to
72  compile for the native CPU using the `-march=native` flag to `g++`.
73 
74 For example, this creates a static configuration for a generix 64-bit CPU without
75 the GUI components, and creates a target build called `server`, which can then be
76 compiled alongside the default `release` build:
77 
78  $ ARCH=x86-64 ./configure -nogui -static server

99 
100 If required, it is also possible to create a configuration by hand. This may be
101 useful in cases where the configuration produced by the configure script does
102 not work as-is, and requires manual editing.
