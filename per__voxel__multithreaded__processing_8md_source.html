1 Running a per-voxel operation on a 4D dataset in a multi-threaded loop {#example_per_voxel_multithreaded_4D_processing}
2 ======================================================================
3 
4 This example computes the matrix multiplication of the vector of intensities
5 for each voxel in the input dataset, producing a new dataset of the same size
6 for the first 3 (spatial) axes, and with the number of volumes specified by the
7 user. In this example, we generate a matrix of random numbers for illustrative
8 purposes.

42 // Use typedefs as in previous example:
43 // I often use two such types: one for the type of the values stored in the
44 // dataset (I typically use float rather than double to keep RAM usage low),
45 // the other for the values used in the computation itself (this often
46 // needs to be higher precision to avoid rounding errors, etc).
47 using value_type = float;
48 typedef float compute_type;
49 
50 
51 
52 // In this case, we also declare a SharedInfo class to hold large data
53 // structures to be accessed read-only by each thread. This reduces the amount
54 // of RAM and especially CPU cache needed by the application at run-time, since
55 // this would otherwise be replicated for each thread (this quickly adds up on
56 // modern multi-core CPUs).
57 class SharedInfo
58 {
59  public:
60  // This creates the matrix to be applied, based on the number of volumes in
61  // the input dataset, and those requested in the output dataset, and fills
62  // it with random numbers from a normal distribution.
63  // Note that I often declare constructors as template functions if the
64  // information from the input image is only needed within the body of the
65  // constructor - i.e. no members are dependent on the type of the input
66  // image - again, this means I don't need to worry about the type of the
67  // image, the compiler will figure this out at compile-time.
68  template <class HeaderType>
69  SharedInfo (const HeaderType& header, size_t num_el) :
70  A (num_el, header.size(3)) {
71  Math::RNG::Normal<value_type> rng;
72  for (ssize_t i = 0; i < A.rows(); ++i)
73  for (ssize_t j = 0; j < A.cols(); ++j)
74  A(i,j) = rng();
75  }
76 
77  Eigen::MatrixXf A;
78 };
79 
80 
81 
82 
83 // This is the functor that will be invoked per-voxel.
84 // Note that here we pass the SharedInfo by const-reference, and construct a
85 // const member reference from it. At this point, the information from the
86 // SharedInfo will be accessible during processing, but only for const access
87 // (read-only), as desired - in general, we really don't want to modify the
88 // information in the SharedInfo during processing, as this will mess
89 // everything up for the other threads.
90 class MathMulFunctor {
91  public:
92 
93  // We pass the SharedInfo class to the constructor, and use it to allocate
94  // thread-local vectors to hold the input and output values. Note that
95  // these vector classes copy-construct appropriately (by deep copy), and
96  // are therefore safe to use here with a default copy constructor.
97  MathMulFunctor (const SharedInfo& shared) :
98  shared (shared),
99  vec_in (shared.A.cols()),
100  vec_out (shared.A.rows()) { }
101 
102  // This is the actual operation to be performed. I use a templated
103  // function, as per the previous example.
104  template <class VoxeltypeIn, class VoxeltypeOut>
105  void operator() (VoxeltypeIn& in, VoxeltypeOut& out)
106  {
107  auto loop = Loop (3);
108 
109  // read input values into vector:
110  for (auto l = loop (in); l; ++l)
111  vec_in[in.index(3)] = in.value();
112 
113  // do matrix multiplication:
114  vec_out = shared.A * vec_in;
115 
116  // write-back to output voxel:
117  for (auto l = loop (out); l; ++l)
118  out.value() = vec_out[out.index(3)];
119  }
120 
121 
122 
123  protected:
124  const SharedInfo& shared;
125  Eigen::VectorXf vec_in, vec_out;
126 };

135 void run ()
136 {
137  // default value for number of output volumes:
138  size_t nvol = get_option_value ("size", 10);
139 
140  // create a Buffer to access the input data:
141  auto in = Image<value_type>::open (argument[0]);
142 
143  // get the header of the input data, and modify to suit the output dataset:
144  Header header (in);
145  header.datatype() = DataType::Float32;
146  header.size(3) = nvol;
147 
148  // create the output Buffer to store the output data, based on the updated
149  // header information:
150  auto out = Image<value_type>::create (argument[1], header);
151 
152  // Create the SharedInfo object:
153  SharedInfo shared (in, nvol);
154 
155  // create a threaded loop object that will display a progress message, and
156  // iterate over buffer_in in order of increasing stride. In this case, only loop
157  // over the first 3 axes (see ThreadedLoop documentation for details):
158  auto loop = ThreadedLoop ("performing matrix multiplication", in, 0, 3);
159 
160  // run the loop, invoking the functor MathMulFunctor that you constructed:
161  loop.run (MathMulFunctor (shared), in, out);
162 }

165 A few tips on how to use the above structure:
166 
167 - Use the `SharedInfo` class to hold any read-only data needed by each thread
168  during execution, and perform all the initialisation required in this class.
169  This helps to keep each thread light-weight by minimising both the amount of
170  RAM each thread needs, and the amount of work each thread needs to do.
171 
172 - If you need each thread to use data types that imply dynamic allocation (e.g.
173  vectors, matrices, etc), declare them as member variables, and if possible
174  allocate them once in the constructor. If these are declared in the body of the
175  `operator()` method, this will probably result in reduced performance due to the
176  cost of allocation/deallocation, as well as the synchronisation calls the
177  memory management infrastructure will need to make to keep its internal data
178  structure in order in a multi-threaded environment.
179 
180 - temporary variables that do not imply dynamic allocation can be declared
181  within the body of the `operator()` method, since these will be allocated on
182  the stack and don't incur a run-time cost.
