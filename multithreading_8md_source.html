1 Writing multi-threaded applications {#multithreading}
2 ===================================
3 
4 Multi-threading allows applications to make use of all available CPU cores
5 on modern multi-core systems, providing an immediate performance boost.
6 MRtrix uses the C++11 threads API to enable multi-threaded processing where
7 possible. To facilitate development of multi-threaded applications, MRtrix
8 includes a number of classes that make it easy for many common workflows.
9 
10 
11 Overview {#multithreading_overview}
12 ========
13 
14 In a nutshell, multi-threading refers to the concurrent execution of a number
15 of light-weight processes (threads) that share a common memory address space.
16 This makes it very easy for processes to process shared data, but also very
17 easy for one process to unexpectedly modify data that other threads are
18 currently operating on. The biggest challenge in multi-threaded programming is
19 managing concurrent access to shared resources and avoiding
20 [race conditions](http://en.wikipedia.org/wiki/Race_condition).
21 Concurrent execution can introduce strange and unexpected bugs, often difficult
22 to reproduce, and whose symptoms are often seemingly unrelated to the original
23 cause. This makes multi-threaded applications very difficult to debug. For this
24 reason, the best approach to developing multi-threaded applications is to keep
25 things simple and clearly organised, and to code with concurrency in mind -
26 even if the class you might be writing is not designed to be used in a
27 multi-threaded context now, it might make sense later.
28 
29 The most common strategy for managing concurrent access is the concept of
30 [mutual exclusion](http://en.wikipedia.org/wiki/Mutual_exclusion>)
31 (a.k.a. mutex). Essentially, this involves identifying any shared resource that
32 threads will need to access, and programming access to this resource in such a
33 way that each thread is guaranteed sole access to the resource while it
34 operates on it. This essentially serialises access to the resource, ensuring
35 that each operation is completed before the next thread is allowed access. For
36 example, iterating through a set of data in a multi-threaded fashion might
37 involve each thread locking a mutex as it fetches the next item of data to be
38 processed from a queue. This ensures that no two threads end up with the same
39 data item to process, that no item accidentally remains unprocessed, etc.
40 
41 How to design a multi-threading application {#multithreading_planning}
42 ===========================================
43 
44 Designing multi-threaded applications requires a different way of programming,
45 both to achieve a simple and robust solution that is not likely to crash, and
46 also to realise the expected performance gains. The single most important
47 aspect in the design process is how to structure the code to clearly define
48 which bits are 'owned' by each thread, which bits are shared across them, and
49 implementing strategies to enforce this design.

53 Sharing read-only data {#multithreading_shared}
54 ======================
55 
56 The approach generally used in MRtrix applications is to define a class to hold
57 data that threads need read-only access to during processing. This class is
58 then initialised prior to creating and launching the threads, and is passed by
59 const-reference to the threads to prevent the threads from unintentionally
60 modifying the data. For example:
61 
62 ~~~{.cpp}
63 class Shared:
64  public:
65  Shared () {
66  // initialise, etc
67  }
68 
69  SomeType shared_parameters;
70  ...
71 };
72 ~~~
73 
74 This class might for example contain all the reconstruction parameters set by
75 the user, and any number of potentially large structures (e.g. matrices) that
76 will be used (but not modified) by the other threads. Once initialised, it is
77 then passed by const-reference to the thread class's constructor:
78 
79 ~~~{.cpp}
80 class Thread {
81  public:
82  Thread (const Shared& shared) :
83  shared (shared) {
84  // any per-thread initialisation
85  }
86 
87  protected:
88  const Shared& shared;
89  OtherType local_variables;
90 };
91 ~~~
92 
93 This structure helps to clearly delineate what is shared across threads and
94 what is private to each thread. Using this construct, each thread class has
95 read-only (const) access to the shared data, and any attempt at non-const
96 access to this data will result in a compile-time failure. This is a very good
97 thing, since trying to debug subtle bugs introduced by race conditions can be
98 very frustrating, and any strategy designed to catch unintended access will
99 save many hours of exasperation further down the track.

102 Sharing read/write data {#multithreading_concurrent}
103 =======================
104 
105 To allow thread-safe read/write access, the lowest-level approach is to design
106 an additional class that encapsulates the data to be protected. This class
107 provides methods to access data items, and manages the mutex associated with
108 the data. For example:
109 
110 ~~~{.cpp}
111 class SharedRW {
112  public:
113  ...
114 
115  Item get_next () {
116  // note: this is pseudo-code!
117  lock_mutex();
118  Item item = list.pop();
119  unlock_mutex();
120  return item;
121  }
122 
123  ...
124 };
125 ~~~
126 
127 In this example, access to the list is protected by locking and releasing a
128 mutex before and after reading the next item from the list, ensuring no two
129 threads can modify the list's internal data structures concurrently (note the
130 `lock_mutex()` & `unlock_mutex()` functions used in this example are for
131 illustration purposes only - no such functions exist within MRtrix).

134 Achieving maximum performance {#multithreading_performance}
135 =============================
136 
137 Ideally, using multi-threading would provide a speedup factor equivalent to the
138 number of cores used. In practice, a number of issues might prevent this from
139 happening. Some of these are hardware-related (e.g. hyper-threading won't give
140 all the performance benefits of a genuine multi-core equivalent CPU), some of
141 them are due to restrictions imposed by the algorithm to be implemented, and
142 some are caused by poor design of the implementation. While the first two are
143 typically unavoidable, there is a lot that can be done for the latter.
144 
145 The first issue to consider is the overhead of the multi-threading calls. Each
146 call to lock or release a mutex will take up CPU cycles due to the function
147 call and the need for the hardware to synchronise across all CPU cores. This
148 overhead can become significant if run within a sufficiently tight loop, where
149 the processing itself might take up fewer CPU cycles than the mutex handling.
150 
151 Another related issue is the cost of holding the mutex, in terms of its impact
152 on other threads. If the mutex is often locked, threads will spend a
153 significant proportion of their time waiting for it to be released. This is
154 particularly the case if the amount of processing done while the lock is held
155 is large in relation to the amount of work done while it is not held.
156 
157 These considerations suggest that optimal performance is achieved by keeping
158 the rate of mutex locking low, and keeping the amount of work done while the
159 lock is held small. This can often be done using simple strategies such as
160 passing pointers to data to be processed, so that pushing or pulling them from
161 a mutex-protected list is quick. If the operation to be performed per item is
162 inherenly small, these can be done in batches to reduce the amount of locking.
163 
164 There are many other issues that can impact performance, such as non-optimal
165 memory access. If each thread is trying to access large amounts of data in
166 seemingly random locations spread all over the RAM, the CPU will probably end
167 up spending a disproportionate amount of time fetching data and flushing the
168 CPU cache, resulting in poor performance. When this happens, multi-threading
169 may seem to provide no benefit, and might in fact adversely affect performance
170 compared to the single-threaded equivalent. It helps to think hard about your
171 code's memory access patterns to take advantage of the CPU's onboard cache and
172 the high burst transfer rates that can be achieved when the CPU can read large
173 chunks of contiguous data. This is even more important when operating on
174 disk-backed data, where the cost of non-linear access can be considerable.

177 Multi-threading API in MRtrix {#multithreading_in_mrtrix}
178 =============================
179 
180 MRtrix provides a number of constructs to simplify the process of writing solid
181 multi-threading applications. In most cases, the high-level

183 for the particular algorithm to be implemented. If a more sophisticated
184 implementation is required, the C++11 threads API can be used directly.

188 Launching threads {#multithreading_exec}
189 =================
190 
191 The MR::Thread::run() function is designed to launch and manage one or more
192 threads. This is done by providing one or more specially-designed thread
193 classes (or functors), whose `execute()` method will be invoked within the
194 newly-created thread. Multiple instances of the same thread class can be
195 launched by wrapping the functor within the `MR::Thread::multi()` call when
196 passing it to MR::Thread::run().
197 
198 @note If the class is to be used in multiple concurrent threads (i.e.
199 launched using MR::Thread::multi()), the class must be copy-constructable,
200 and any copy created in this way must be fully independent: if pointers to
201 non-const data or other complex structures are members of the class, there is a
202 good chance the default copy constructor will provide a copy referencing the
203 same data as the original, which would generally lead to race conditions if
204 these were written to during processing. Most of the classes provided in MRtrix
205 do copy-construct appropriately for use in multi-threading (for example
206 [Image], [Adapter]), while others do not). That said, if all class members have
207 appropriate copy constructors, the default copy constructor should also be
208 appropriate.
209 
210 For example:
211 
212 ~~~{.cpp}
213 class MyThread {
214  public:
215  void execute() {
216  // do stuff
217  }
218 };
219 
220 
221 void run() {
222  MyThread thread;
223  auto exec = Thread::run (thread, "my thread");
224 
225  ...
226  // do something else
227  ...
228 
229  // invoking thread will wait for other thread to finish (join)
230  // in the thread class's destructor - i.e. when thread goes out of scope
231 }
232 ~~~
233 
234 To run it across multiple threads, use the MR::Thread::multi() wrapper. By
235 default, the number of threads launched is determined from the C++11
236 `std::thread::hardware_concurrency()` function, from the config file or from the
237 command line.
238 
239 ~~~{.cpp}
240 void run () {
241  MyThread thread;
242 
243  auto exec = Thread::run (Thread::multi (thread), "my threads");
244 
245  ...
246  // do something else, or just wait for completion.
247  ...
248 
249  // invoking thread will wait for all other threads to finish (join)
250  // in thread class's destructor - i.e. when exec goes out of scope
251 }
252 ~~~

256 The ThreadedLoop {#multithreading_loop}
257 ================
258 
259 It is very common in imaging to process image voxels. The MR::ThreadedLoop()
260 function and associated classes are designed to greatly simplify the process of
261 creating such applications. It allows the developer to provide a simple functor
262 class implementing the operation to be performed for each voxel, which can be
263 passed to MR::ThreadedLoop() to be executed over the whole dataset. Refer to
264 @ref image_thread_looping documentation for more information.

269 The Thread::Queue {#multithreading_queue}
270 =================
271 
272 In many cases, an algorithm can be designed to process a stream of data. For
273 example, data items are read in order from disk, and can be processed
274 independently. The results might then need to be written back to disk in a
275 serial fashion. The MR::Thread::Queue class is designed to facilitate this type
276 of operation. Please refer to the @ref thread_queue for a detailed description.
277 
278 There is also a convenience function to simplify the setting up of
279 the queue structure, called MR::Thread::run_queue(). This also works with the
280 MR::Thread::multi() wrapper where multiple parallel threads are desired.
281 Please refer to the [Thread module documentation[(@ref thread_classes) for details.
