1 The build process {#build_page}
2 =================
3 
4 The procedure used to compile the source code is substantially different from
5 that used in most other open-source software. The most common way to compile a
6 software project relies on the `make` utility, and the presence of one or
7 several `Makefiles` describing which files are to compiled and linked, and in
8 what order. The process of generating the `Makefiles` is often facilitated by
9 other utilities such as `autoconf` & `automake`. One disadvantage of this
10 approach is that these `Makefiles` must be updated every time changes are made
11 to the source code that affect the dependencies and the order of compilation.
12 
13 In MRtrix, building the software relies on a two-stage process implemented in
14 Python. First, the `configure` script should be executed to set the relevant
15 architecture-specific variables (see @ref configure_page for details). Next,
16 the `build` script is executed, and is responsible for resolving all
17 inter-dependencies, then compiling and linking all the relevant files in the
18 correct order. This means that any new files added to the source tree will be
19 compiled if needed (according to the rules set out below), without any further
20 action required. In addition, this script is multi-threaded and will use all
21 available CPU cores simultaneously, significantly reducing the time needed to
22 build the software on modern multi-core systems.
23 
24 @note on systems with a large number of cores but comparatively small amount
25 of RAM, the multi-threaded build can run out of memory. In these cases, it may
26 be necessary to reduce the number of threads used by the build script by setting
27 the `NUMBER_OF_PROCESSORS` environment variable before invoking `./build`.
28 
29 Using the MRtrix build process {#build_process_usage}
30 ==============================
31 
32 The build scripts used to build MRtrix applications are designed to be
33 easy to use, with no input required from the user. This does mean that
34 developers must follow a few fixed rules when writing software for use
35 with MRtrix.
36 
37 - To create a new executable, place the correspondingly named source file
38  in the `cmd/` folder. For example, if a new application called `myapp`
39  is to be written, write the corresponding code in the `cmd/myapp.cpp`
40  source file, and the build script will attempt to generate the executable
41  `release/bin/myapp` from it. You may want to consult the section @ref
42  command_howto for information on the contents of a command.
43 
44 - The `lib/` folder should contain only code destined to be included into
45  the MRtrix shared library. This library is intended to provide more
46  generic image access and manipulation routines. Developers should avoid
47  placing more application-specific routines in this folder.
48 
49 - Code designed for specific applications should be placed in the `src/`
50  folder. The corresponding code will then be linked directly into the
51  executables that make use of these routines, rather than being included
52  into the more general purpose MRtrix shared library.
53 
54 - Non-inlined function and variable definitions should be placed in
55  appropriately named source files (`*.cpp`), and the corresponding
56  declarations should be placed in a header file with the same name and the
57  appropriate suffix (`*.h`). This is essential if the build script is to resolve
58  the correct dependencies and link the correct object files together.
59 
60 - MRtrix headers or any header added by the user must be included within
61  quotes, and any system headers within angled brackets. This is critical for
62  the build system to work out the correct dependencies (see @ref include_path
63  for details).

67 The configure script {#configure_section}
68 ====================
69 
70 The first step required for building the software is to run the `configure`
71 script, which tailors various parameters to the specific system that it is run
72 on. This includes checking that a compiler is available and behaves as
73 expected, that other required packages are available (such as Eigen), whether
74 the system is a 64-bit machine, etc. It is also possible to create distinct
75 co-existing configurations, for example to compile either release and debug
76 code. For details, see @ref configure_page.

79 The build script {#build_section}
80 ================
81 
82 This script is responsible for identifying the targets to be built, resolving
83 all their dependencies, compiling all the necessary object files (if they are
84 out of date), and linking them together in the correct order. This is done by
85 first identifying the desired targets, then building a list of their
86 dependencies, and treating these dependencies themselves as targets to be built
87 first. A target can only be built once all its dependencies are satisfied (i.e.
88 all its required dependencies have been built). At this point, the target is
89 built only if one or more of its dependencies is more recent than it is itself
90 (or if it doesn't yet exist). This is done by looking at the timestamps of the
91 relevant files. In this way, the relevant files are regenerated only when and
92 if required.
93 
94 The following rules are used for each of these steps:
95 
96 #### Identifying targets to be built
97 
98 Specific targets can be specified on the command-line, in which case only
99 their minimum required dependencies will be compiled and/or linked. This
100 is useful to check that changes made to a particular file compile without
101 error, without necessarily re-compiling all other associated files. For
102 example:
103 
104  $ ./build release/bin/mrconvert
105  $ ./build lib/mrtrix.o lib/app.o
106 
107 
108 If no specific targets are given, the default target list will be generated,
109 consisting of all applications found in the `cmd/` folder. For example, if the
110 file `cmd/my_application.cpp` exists, then the corresponding target
111 `release/bin/my_application` will be included in the default target list.
112 
113 #### Special target: _clean_
114 
115 The special target `clean` can be passed to the `build` script to remove all
116 system-generated files, including all object files (`*.o`), all executables
117 (i.e. all files in the `release/bin/` folder), and the MRtrix shared library.
118 
119 #### Resolving dependencies for executables
120 
121 A target is assumed to correspond to an executable if it resides in the
122 `release/bin/` folder (the default target list consists of all executables).
123 The dependencies for an example executable \c release/bin/myapp are resolved in
124 the following way:
125 
126 1. the MRtrix library `lib/mrtrix-X_Y_Z.so` is added to the list
127 
128 2. the object file `cmd/myapp.o` is added to the list
129 
130 3. a list of all local headers included in the source file `cmd/myapp.cpp` is
131  generated. A header is considered local if it is included using inverted
132  commas rather than angled brackets. For example:
133  ~~~{.cpp}
134  // By default, the lib/ & src/ folders are included in the include search path
135  #include "mrtrix.h" // the file lib/mrtrix.h exists, and is considered a local header
136  #include <iostream> // this file is not considered local
137  ~~~
138 
139 4. if a corresponding source file is found for any of these headers, its
140  corresponding object file is added to the list. For example, if
141  `cmd/myapp.cpp` includes the header `src/histogram.h`, and the file
142  `src/histogram.cpp` exists, the object file `src/histogram.o` is added to the
143  list of dependencies. Note that object files in the `lib/` folder are not
144  added to the list of dependencies, since they should already be included
145  in the MRtrix library (see below).
146 
147 5. all headers included in any of the local headers or their corresponding
148  source files are also considered in the same way, recursively until no new
149  dependencies are found. For example, the file `src/histogram.cpp` might also
150  include the header `src/min_max.h`. Since the source file `src/min_max.cpp`
151  exists, the corresponding object file `src/min_max.o` is added to the list.
152 
153 #### Resolving dependencies for object files
154 
155 A target is considered to be an object file if its suffix corresponds to the
156 expected suffix for an object file (usually `*.o`). The dependencies for an
157 example object file `lib/mycode.o` are resolved as follows:
158 
159 1. the corresponding source file \c lib/mycode.cpp is added to the list
160 
161 2. a list of all local headers included in the source file `lib/mycode.cpp` is
162  generated.
163 
164 3. the list of local headers is expanded by recursively adding all local
165  headers found within the already included local headers, until no new
166  local headers are found.
167 
168 4. these headers are all added to the list of dependencies.
169 
170 #### Resolving dependencies for the MRtrix library
171 
172 The list of dependencies for the MRtrix library is generated by adding the
173 corresponding object file for each source file found in the `lib/` folder. For
174 example, if the file `lib/image/header.cpp` is found in the `lib/` folder,
175 the object file `lib/image/header.o` is added to the list of dependencies.
176 
177 #### Build rules for each target type
178 
179 - **executables:** dependencies consist of all relevant object files along with
180  the MRtrix library. These are all linked together to form the
181  executable.
182 
183 - **object files:** dependencies consist of a single source code file, along
184  with all the included headers. The source code file is compiled to form the
185  corresponding object file.
186 
187 - **MRtrix library**: dependencies consist of all the object files found in the
188  `lib/` folder. These are all linked together to form the shared library.
189 
190 - **source & header files:** these have no dependencies, and require no action.
